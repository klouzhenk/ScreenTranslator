# Файли-контейнери з кількома варіантами

## Принцип
Один файл, усередині — кілька представлень того самого «логічного» ассета + заголовок-таблиця, яке представлення де лежить. OS, застосунок чи рендерер при звертанні каже «мені треба X» і контейнер віддає потрібний варіант. Зовнішньо — одна одиниця, яку копіюєш, посилаєшся і trackaєш.

Патерн повторюється в різних форматах і техніках. Це варто знати, бо ім'я одне, а внутрішня механіка однакова.

## Приклади в графіці

| Формат | Що містить | Для чого |
|---|---|---|
| **`.ico` (Windows)** | До ~10 bitmap'ів розмірностей 16–256 | Іконки застосунків. Один `.ico`, Windows вибирає розмір під контекст (трей 16, Alt+Tab 32, «Велетенська іконка» в Explorer 256) |
| **`.icns` (macOS)** | Bitmap'и 16–1024 | Іконки застосунків на macOS. Те саме, але стеля розмірності вища |
| **`.cur` / `.ani` (Windows)** | Bitmap курсора + hotspot (точка «пера»); `.ani` ще й кадри анімації | Курсори мишки |
| **Multi-page TIFF** | Багато сторінок / розмірностей / каналів | Факси, сканери, медичні знімки (КТ, МРТ) |
| **HEIC / HEIF** | Серії фотографій (burst), фото + depth map, thumbnail + full-res | Live Photos на iPhone, портретний режим |
| **Mipmap у DDS/KTX** | Та сама текстура в 1024, 512, 256, 128, 64… | 3D-ігри: GPU бере дрібнішу копію при віддаленні камери, швидко |
| **Font (`.ttf`/`.otf`)** | Вектори гліфів + іноді bitmap strikes для малих кеглів + hinting | Шрифти, що виглядають чітко і в 8pt, і в 72pt. У `.otf/.ttf` є навіть color tables для емоджі |

## Устрій `.ico` (конкретика)
Заголовок файла — 6 байт (reserved, type, кількість зображень). Далі таблиця `ICONDIR` entries — по 16 байт на кожен варіант: ширина, висота, bpp, offset у файлі, size. Потім — сам контент: або звичайний BMP, або PNG (для `.ico` ≥ 48, часто PNG, щоб менше місця займало).

Поле ширини/висоти — 1 байт (0–255). Число 0 означає **256** (бо 256 в один байт не поміщається). Звідси історична межа «`.ico` до 256 пікселів» — байтовий overflow на рівні структури файла. Ніхто не хотів ламати backward compatibility, тому 512 чи 1024 в `.ico` немає й не буде.

## Чому один файл замість багатьох

**Альтернатива — окремі файли.** Так робить web (`favicon-16.png`, `favicon-32.png`, `apple-touch-icon-180.png`) і Android (`drawable-mdpi/`, `drawable-xhdpi/`, `drawable-xxhdpi/`).

| | Окремі файли + manifest | Контейнер із варіантами |
|---|---|---|
| Простота формату | Кожен файл — звичайний PNG, редагується будь-де | Складніший, потрібен спеціальний editor |
| Reference у коді | Треба десь зберігати мапу «який для якого контексту» (HTML `<link>`, JSON-manifest, build-conventions) | Один reference, OS/рантайм сам обере |
| Втрата варіанта | Легко забути виміряти одну розмірність, зламається тихо | Все атомарно — або весь файл, або нічого |
| Копіювання / деплой | Треба пам'ятати, що це набір файлів | Один `.ico` — одна одиниця |

Для системних речей (іконки OS, курсори, шрифти) — переважає контейнер. Для web — окремі файли, бо кожен запит однаково окремий HTTP-call, нічого не виграєш.

## Вектор як третій шлях

**SVG — геть інша філософія: один файл, нескінченні розмірності.** Там не записано «ось 16, ось 32, ось 256», а записано команди типу «коло радіусом 10, лінія від (5,5) до (15,15)». Рендериться в будь-який розмір на льоту без втрати якості.

Переваги: один маленький файл обслуговує все, вектор ніколи не пікселізує.
Обмеження:
- Рендер у рантаймі коштує CPU-часу (не критично для статичних іконок, важливо для багатьох об'єктів).
- У малих розмірах (16x16) тонкі лінії вектора можуть виглядати гірше, ніж вручну зроблений bitmap саме для 16x16 (hinting, ручне розставляння пікселів).
- Нативні десктопи (Windows, macOS) досі НЕ підтримують SVG як формат exe-іконки. Треба експортувати в `.ico` / `.icns` при білді.

Web, Flutter, Jetpack Compose, modern mobile — підтримують SVG як first-class. Windows WPF — через `DrawingImage`/XAML Paths, але не з file.svg напряму.

## Споріднений патерн поза графікою

Той самий принцип «контейнер + таблиця вмісту» зустрічається де завгодно:

| Формат | Що всередині |
|---|---|
| **MKV (video)** | Один відеотрек + кілька аудіодоріжок + субтитри кількома мовами + chapters |
| **Universal binary (macOS `.app`, iOS `.ipa`)** | Один exe, усередині x86_64 і arm64 машинний код, OS бере свій |
| **Fat binary / multi-arch Docker image** | Один image tag, під капотом окремі layer-и для linux/amd64, linux/arm64, linux/arm/v7 |
| **ZIP-подібні контейнери** — `.docx`, `.xlsx`, `.pptx`, `.apk`, `.jar`, `.nupkg`, `.ipa` | Файл-який-архів, усередині XML / class-файли / ресурси |
| **Microsoft CAB** | Старий Windows-архів для installer-пакетів |
| **Self-contained single-file .NET exe** (див. [release-publishing.md](release-publishing.md)) | Один exe, всередині managed dll'ки + CLR runtime |

Універсальна структура: **заголовок → index / таблиця → payload блоки**. Хто написав парсер для одного — легко пише для інших, бо ідея та сама.

## Mental model
«Один logical asset, кілька physical representations, контейнер із таблицею-картою» — патерн, який повторюється на всіх рівнях: від растрових іконок до exe-файлів і Docker-образів. Коли бачиш новий формат з розширенням, якого не знаєш — варто перевірити, чи він не з цієї сім'ї. Часто відповідь — так.
