# Нотатки: Access modifiers у C#

У C# є **шість** модифікаторів доступу, а не три. Різниця між «у межах збірки» і «назовні» важить у багатопроєктних застосунках і бібліотеках — звідти беруться `internal`, `private protected`, `protected internal` і `file`, яких у «публічному» наборі `public` / `private` / `protected` немає.

## Повний список

| Модифікатор | Доступно звідки | Пам'ятка |
|---|---|---|
| `public` | Звідусюди | API бібліотеки або те, що мусять бачити зовнішні споживачі. |
| `internal` | Тільки в межах тієї ж збірки (assembly) | **Для застосунків — default вибір.** |
| `protected` | Клас + будь-який нащадок (у тому числі в іншій збірці) | Контракт для нащадків: hook, template method в базовому класі. |
| `private` | Тільки в межах того самого типу | Деталь реалізації класу. |
| `private protected` | Нащадки **і** в тій самій збірці (AND) | Hook для нащадків у межах своєї ж бібліотеки, зовні закрито. |
| `protected internal` | Нащадки **або** в тій самій збірці (OR) | Рідко. API, яке бібліотека підказує нащадкам + своїм же компонентам. |
| `file` (C# 11+) | Тільки в межах одного `.cs`-файлу | Згенерований helper, якого не має бачити навіть інший файл цієї ж збірки. |

## Default modifiers

Коли не пишеш модифікатор — компілятор підставляє свій дефолт:

| Де | Default |
|---|---|
| Top-level типи (`class` / `interface` / `enum` / `record` / `struct`) | `internal` |
| Члени `class` і `struct` | `private` |
| Члени `interface` | `public` |
| Члени `enum` | `public` (інше не має сенсу) |
| Nested type в класі/структурі | `private` |

Тобто `class Foo {}` без модифікатора — це `internal class Foo {}`. Хочеш public — пиши явно.

## Коли яке брати для застосунків

Правило: **`public` тільки те, що є договором з іншою збіркою.** Якщо застосунок — один `.exe`-проєкт без зовнішніх споживачів, `public` на типах узагалі не потрібен (окрім того, що генерує XAML / spec). За замовчуванням — `internal`.

У нашому ScreenTranslator після рефакторингу:
- WPF-партіали `App`, `ResultWindow`, `SelectionWindow` — `public` (XAML generator вимагає).
- Все інше — `internal`. Інтерфейси сервісів, записи, Options, exceptions, DI extensions.
- Приватна поведінка класу — `private`.
- `protected` використано тільки для override-ів у WPF (`OnSourceInitialized`, `OnMouseDown`, …).

## Коли яке брати для бібліотек (NuGet, SDK)

Протилежна дисципліна: **`public` — тільки те, що точно хочеш підтримувати.** Усе, що `public`, стає твоїм контрактом; зміниш — зламаєш споживачів. Решту ховай у `internal`. `InternalsVisibleTo` у `.csproj` відкриває доступ довіреним збіркам (напр., тестовому проєкту) без розкриття інкапсуляції для сторонніх:

```xml
<ItemGroup>
    <InternalsVisibleTo Include="ScreenTranslator.Tests" />
</ItemGroup>
```

## Коли `file`

Рідко. Корисно для:
- source generator-ів, які створюють типи-хелпери і не хочуть глобалити імена,
- локальних хелпер-типів, щоб два згенеровані файли не конфліктували іменами.

Звичайному коду зазвичай не треба.

## Поширений антипатерн

Писати всюди `public` «на всякий випадок». У перегляді компільованого коду `public static void M()` всередині internal-класу ефективно поводиться як `internal` — але читати важче, IDE не підказує, рефакторити боляче. **Внутрішня модель збірки має бути `internal`**, а не «public всередині internal класу».
