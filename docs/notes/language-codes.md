# Нотатки: Коди мов (ISO 639, BCP-47)

Коли працюєш з текстом, рано чи пізно впираєшся в питання «а якою мовою вказувати мову?». Різні API очікують різні стандарти, і якщо переплутаєш — тихо вилізе баг, який складно знайти.

## Стандарти

### ISO 639 — коди мов

Три рівні, різна довжина, різне покриття:

| Стандарт | Довжина | Покриття | Приклад |
|---|---|---|---|
| **ISO 639-1** | 2 літери | ~184 найпоширеніших мов | `en`, `uk`, `ja`, `de`, `fr` |
| **ISO 639-2** | 3 літери | ~500 мов | `eng`, `ukr`, `jpn`, `deu` |
| **ISO 639-3** | 3 літери | ~8000 мов (включно з рідкісними і мертвими) | `eng`, `ukr`, `cmn` (мандаринська) |

ISO 639-1 покриває все, що потрібно 99% API. Якщо потрібна рідкісна діалект або мертва мова — ISO 639-3.

### ISO 15924 — коди писемностей

4 літери, перша велика: `Latn` (латиниця), `Cyrl` (кирилиця), `Hans` (китайська спрощена), `Hant` (китайська традиційна), `Jpan` (японська — мікс кандзі + кана), `Hani` (кандзі).

### ISO 3166 — коди країн/регіонів

2 літери, великими: `US`, `GB`, `UA`, `JP`, `BR`.

### BCP-47 — композиція попередніх

Стандарт IETF (Best Current Practice 47), який складає **мова-писемність-регіон**, через дефіс:

```
<language>[-<script>][-<region>][-<variant>]
```

Приклади:
- `en` — просто англійська (без регіону)
- `en-US` — англійська, США
- `en-GB` — англійська, Британія
- `uk-UA` — українська, Україна
- `zh-Hans` — китайська, спрощене письмо (без прив'язки до країни)
- `zh-Hans-CN` — китайська, спрощена, материковий Китай
- `zh-Hant-TW` — китайська, традиційна, Тайвань
- `ja-JP` — японська, Японія
- `sr-Cyrl-RS` — сербська, кирилиця, Сербія (на противагу `sr-Latn-RS` — сербська латиницею, Сербія)

Writing систему вказують **тільки коли мова має дві й більше**: китайська (Hans/Hant), сербська (Cyrl/Latn), узбецька (Latn/Cyrl). Для англійської, української, японської — не треба (одна).

## Чому стільки стандартів і як вибирати

Коротко: **вони не конкурують, а доповнюють одна одну на різних осях**. Суперечать не стандарти між собою, а API, які їх інтерпретують по-своєму.

### Як вони пов'язані

```
ISO 639-1 ⊂ ISO 639-2 ⊂ ISO 639-3      — таксономія мов, від звичайного до рідкісного
ISO 15924                              — ОКРЕМА вісь: писемності
ISO 3166                               — ОКРЕМА вісь: країни / регіони

BCP-47 ─ не окремий стандарт мов, а СКЛАДАЛЬНА інструкція:
         <мова з ISO 639>-<script з 15924>-<регіон з 3166>
```

BCP-47 не замінює ISO 639 — він його використовує. Як `List<T>` не замінює `T` — він його обгортає. Щоразу, коли бачиш `en-US`: `en` з ISO 639-1, `US` з ISO 3166. Один блок з двох стандартів.

### Чому три рівні ISO 639

Це не «новий замість старого» — це **різна деталізація для різних задач**:

- `639-1`: 2 літери для ~184 мов → web, translation API, UI.
- `639-2`: 3 літери для ~500 → бібліотечні каталоги (Library of Congress).
- `639-3`: 3 літери для ~8000 → лінгвістика, SIL International, умираючі мови.

Для застосунку-перекладача достатньо `639-1`. Для лінгвіста, який описує діалект Амазонки — потрібен `639-3`. Обидва стандарти живі одночасно.

### Суперечності не між стандартами, а в реалізаціях

Самі документи ISO 639 / 15924 / 3166 / BCP-47 несуперечливі. **Протиріччя виникають у тому, як API їх використовують** — DeepL пише `UK` замість `uk`, Google іноді `zh-CN` замість правильного `zh-Hans`, деякі парсери ковтають `en-us` lowercase (деталі в розділі «Пастки» нижче).

### Правило, який коли дотримуватися

Зверху-вниз за пріоритетом:

1. **Документація конкретного API** → той формат, який там указано. Головне правило. DeepL каже `UK` — значить `UK`.
2. **Усередині свого коду** → **BCP-47** як canonical. Повний, сучасний, `CultureInfo` в .NET його розуміє з коробки.
3. **На межі системи (конфіги, DTO)** → залежить від читача. Для людини — BCP-47 звичніший, бо збігається з HTML і OS.
4. **Коли два API потребують різних форматів** → **два окремих поля в конфізі**, як у нас (`OcrOptions.Language` і `TranslationOptions.{Source,Target}Lang`). Конвертер «на льоту» (`"en-US"` → `"EN"` через відрізання) — анти-патерн: приховує, що формати різні, легко ламається на новій мові.

## Хто що очікує

| API / платформа | Формат | Приклад |
|---|---|---|
| **Windows.Media.Ocr** (клас `Windows.Globalization.Language`) | BCP-47 | `en-US`, `uk-UA`, `ja-JP` |
| **.NET `CultureInfo`** | BCP-47 | `en-US`, `uk-UA` |
| **DeepL API** | ISO 639-1 (uppercase) | `EN`, `UK`, `JA` |
| **Google Translate API** | BCP-47 (інколи плоский ISO 639-1) | `en`, `zh-CN` |
| **HTML `lang=`** | BCP-47 | `<html lang="uk-UA">` |
| **HTTP `Accept-Language`** | BCP-47 з quality | `uk-UA,uk;q=0.9,en;q=0.5` |
| **gettext `.po`** | POSIX-style (історично) | `uk_UA.UTF-8` (не плутати з BCP-47) |

## Пастки

1. **Case sensitivity.** BCP-47 формально case-insensitive, але конвенція: `en-US`, не `EN-us`. DeepL навпаки — завжди uppercase (`EN`, `UK`). Писати в нижньому регістрі в DeepL — працює, але нестандартно, тому бібліотека SDK може нормалізувати.

2. **Регіон у перекладі зазвичай не важить.** DeepL все одно `en-US` чи `en-GB` — результат той самий. А ось для TTS (text-to-speech) або orthography checker'а — різниця велика.

3. **Китайська різне.** `zh` сам по собі неоднозначний: Hans (сходу спрощено) чи Hant (Тайвань, Гонконг). Тому в BCP-47 почали явно вимагати writing: `zh-Hans`, `zh-Hant`. Вкажеш просто `zh` — платформа вгадає (зазвичай Hans).

4. **Українська у DeepL.** `UK` = Ukrainian в DeepL. Але у стандарті ISO 639-1 `UK` **не існує**! Українська — `uk`. `UK` як регіональний код у ISO 3166 означає **United Kingdom** (хоча Британія формально `GB`, `UK` — reserved). DeepL використовує `UK` для української через... історичні причини, напевно.

   Отже:
   - DeepL: `TargetLang = "UK"` → українська ✅
   - Windows OCR: `new Language("uk-UA")` → українська ✅
   - Якщо спробуєш у DeepL `TargetLang = "uk"` — може працювати через SDK normalization, а може кинути `AuthorizationException`-подібне. Строго — `UK`.

## У нас

Два окремі `IOptions`-класи, бо формати принципово різні:

| Config | Приклад | Стандарт | Куди йде |
|---|---|---|---|
| `OcrOptions.Language` | `"en-US"` | BCP-47 | `new Language(...)` у Windows.Media.Ocr |
| `TranslationOptions.SourceLang` | `"EN"` | ISO 639-1 (uppercase, DeepL-style) | DeepL SDK |
| `TranslationOptions.TargetLang` | `"UK"` | ISO 639-1 (uppercase, DeepL-style) | DeepL SDK |

Якщо б зліпили в один `SourceLang = "en-US"` — довелось би написати конвертер «відрізати хвіст після дефіса і зробити UPPER». Приховує намір, легко загубити при додаванні нової мови. Два окремі config типи кажуть читачеві: «тут BCP-47, а тут ISO 639-1», і компілятор не плутає їх.
